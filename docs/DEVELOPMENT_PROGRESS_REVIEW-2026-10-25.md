## 一、总体结论

**项目已经超过基础原型，处于“核心功能基本成型，正在完成集成验收和比赛提交”的阶段。** 算法和基准测试是目前最扎实的部分；主要缺口是网页端跨建筑与建楼流程、完整演示视频，以及 Sunday 专项输入输出适配。不能认定为所有挑战均已完成。

如果目标是证明核心算法和代理能力，项目已有较强基础；如果目标是交付一套评委可以顺畅体验、完整复现的最终作品，还需要一轮集成与发布收尾。

不建议给出单一完成百分比：底层算法、网页集成、实际交互和比赛交付的成熟度存在明显差异，简单平均会掩盖关键缺口。

## 五、关键未完成项

### 5.1 网页“导入建筑后直接导航”尚未闭环

`frontend/src/features/building-ingestion/PlanImport.tsx` 对图片/PDF 的处理主要是显示比例和标高输入，尚未完成上传、后端提取、审阅及保存建筑的完整流程。

JSON 导入主要更新前端本地状态；`frontend/src/app/App.tsx` 对导入建筑的寻路明确返回 `importedNoRoute`，未为该建筑创建可寻路的后端会话。

因此，应评价为有导入界面和预览，也有独立 CLI 建楼能力，但尚未串成完整网页功能。关键位置：`PlanImport.tsx:23`、`App.tsx:173`、`App.tsx:367`，行号以审查时版本为准。

### 5.2 跨建筑路线需要 CLI 展示

校园图和步道算法已有可运行结果，网页仍只加载一栋建筑。“底层支持跨建筑”成立，“网页已支持统一跨建筑导航”尚不成立。[演示运行记录](DEMO_RUN-2026-10-25.md) 已明确此限制。

### 5.3 建楼验收复杂度有限

已有简单两层图的提取、审阅与应用记录，但验证路线是 F0-S1 → F0-S2 的同层路线，没有生成层间连接器。因此，尚不能声称复杂多层实际建筑已经能够被可靠自动重建并跨层导航。

`final_agent/plan_build.py` 的 PDF 处理限制为每次单页，多页需要按楼层分别输入。缺少比例时要求校准，是合理的安全边界。

默认 kit 路由还继承了断连室内几何情况下的 1.5 倍直线距离估算。这种结果不是可绘制的有效路径，展示时需要保留其估算属性，不能将其解释为已验证的真实通道。

### 5.4 Sunday 专项适配仍是占位保护

`benchmark/sunday.py` 当前会解释 schema 尚未记录，然后返回失败，不生成答案文件。这避免了伪造格式，但还不是可运行的 Sunday 答题管线。

PDF 对新建筑的 `questions.json → answers.json` 要求，与当前已生成的 145 题 CSV 提交需要分开看。主办方最终 schema 是否已经发布，需要另行确认，不能仅依据仓库记录推断外部发布状态。

### 5.5 演示和语音交付仍需验收

现有文档明确记录没有生成演示视频，69.98 秒的验收过程中也没有在浏览器打开 3D。尚缺全部重点能力在一套连续用户流程中完成的证据。

3D 是当前最适合集中展示的扩展。语音具有适配器、界面和模拟提供方测试，但真实麦克风 → 识别 → 导航 → 语音播报链路没有验收证据；不能仅据历史问题记录认定它当前已坏，也不能仅据单元测试认定其已经可用。

## 六、建议的收尾顺序

1. **完成评委可见的主流程。** 定位 → 无障碍路线 → 关闭路径 → 重算 → 地图更新。跨楼和建楼若继续使用 CLI，应在说明和演示中明确切换方式。
2. **完成连续演示与视频。** 将最成熟的 3D 纳入实际展示，保留可复现命令和明确的能力边界。
3. **完成 Sunday 适配。** 按主办方最终 schema 接入、验证并生成所需答案文件；不能将当前失败退出的命令标记为完成。
4. **冻结并核对交付版本。** 审查时分支相对本地跟踪分支显示 ahead 35，且有大量未提交改动和产物；这不是对远端实时状态的确认。应核对最终仓库包含已验证内容，并检查干净检出后的可复现性。
5. **暂缓新扩展。** 优先完成现有主线和交付，不建议继续分散到新的可选功能。
